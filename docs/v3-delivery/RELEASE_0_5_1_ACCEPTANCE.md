# 0.5.1 完整升级验证（2026-09-23）

本轮按用户确认的框架升级方案交付：完整替换程序，保留旧数据，不自动导入旧配置、词库和历史。固定 fdfd829 候选的整轮验证及下载校验已通过；真实目标应用与实体手机验收仍未完成，尚未公开发布。

## 行为变化

- 发布包同时提供 Setup、便携 ZIP 和 `DoubaoTypeless.exe` 完整升级入口。两个外层 EXE 使用同一原生载荷；旧更新器把任意一个 EXE 改成旧程序名后，都能进入完整升级路径。
- 新入口部署全部运行文件，使用干净的 PyInstaller 环境启动新版。只有收到对应构建的就绪回执后，才切换安装入口。
- 新版设置支持下载、取消和重启更新。下载经过大小及 SHA-256 校验；交接通过独立的就绪、接受、撤销文件，避免当前程序未确认时自行安装。
- 已安装版本在解压或启动失败时尝试恢复旧进程。便携版成功升级后原入口转为新版入口，原 EXE 另存备份，旁边的数据不改动。
- 已发布的 0.4.2 客户端不能被远程修补。它在下载和退出之前的既有故障仍可能需要手动运行完整升级包；不能声称旧更新器所有故障均已消除。

## 验证方式与边界

实际旧版检查使用 GitHub 已发布的 v0.4.2 EXE，不替换其更新器代码。测试服务器提供本轮完整包，临时 HTTPS 信任仅传给测试子进程，不安装系统证书；通过真实更新确认按钮执行下载、退出、替换和重启。

该验证只在一次性的 GitHub Windows 桌面运行，使用测试安装注册项、独立数据目录和本机控制管道。旧数据逐字节核对；重复打开旧入口还需要保持同一运行 PID、同一构建身份，并且不重新解压带时间标记的文件。

原生失败恢复使用明确标注的轻量测试程序，验证错误构建、解压冲突、外来非空目录、入口占用和重复打开。该部分不冒充真实 0.4.2 或完整客户端体验。

## 本轮发现及修正

- 第一次原生浏览器检查遇到按钮位置被遮挡，禁止点击的保护生效；保留失败证据。
- 第二次在切换输入框场景失败，尚不能单凭当时结果判断产品问题或网页脚本切焦点的时序问题。后续改用真实鼠标切换，并等待 Windows 可访问性焦点确认，仍要求两个输入框都不得收到误贴内容。
- 新验证脚本曾错误引用打包测试环境不存在的源码模块，已改为调用 Windows 自身的按键状态接口。
- 独立源码复核指出原文件时间不足以证明没有重复安装，已增加进程身份和有区分度的文件时间标记。
- 原安装回归样例 `previous-test.exe` 被新命名规则识别为自动升级入口；样例本来只验证普通安装布局，现明确命名为 `previous-test_Setup.exe`。原生各项独立检查在已有包时继续执行，但任何失败仍使整个流水线失败。
- 官方旧版更新确认框刚出现时的一次点击未生效，现要求按钮可见、无遮挡、位置稳定，并验证点击后原确认框关闭。
- e53e253 的实际旧版运行走了计划任务兜底：下载、退出、替换和启动新版均已发生，截图显示 0.5.1 e53e2534。但计划任务不继承测试环境变量，脚本去了错误目录检查，也未清理到已启动的新进程，影响了随后浏览器检查。现把隔离安装路径、数据目录和控制管道只在 TEST_INSTALL 中编译进测试包；生产安装包不包含这些测试路径。完整通过结论仍以修正后的整轮结果为准。
- 15623e8 已确认官方旧版完整下载、正常退出、入口替换、新版就绪、旧数据不变。重复打开检查发生在安装器仍持有互斥句柄时，现明确等待安装事务结束，再检查重复打开。
- 同轮原生图文检查发现真实的延迟附件焦点竞争：两张图已发送，正文前附件才自动获得焦点，单次图片后恢复无法覆盖。现在每个后续粘贴边界复用原有的受限恢复；仅本轮已经发送图片时允许，仍检查原输入框、原容器与用户输入时间戳，用户主动切换目标会停止。新增 8 项时序及拒绝恢复回归，相关 37 项本地测试通过。
