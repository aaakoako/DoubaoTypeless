# DoubaoTypeless V3：从设计执行到可发布候选

日期：2026-09-18。对照：原 Pocket Composer v3 方案；已审计代码 `9dd3a369f1b566d0fdc548cee3af934523e9b8db`。

本契约没有审查晚于上述SHA的新提交，没有重新证明旧审计的Windows/真机结论。用户目标是做完整个V3、好用、可发布，而不是让他手动指挥24次。

## 1. 原交付方式哪里需要改

原产品方案已有明确的轻量浮窗、手机单页Composer、截图标注、白板、先图后文、召回和安全要求。问题不是这些全没写，而是执行方式与交付出口不匹配。

- 旧启动指令写“只执行V3-00，完成后停止”，还要求后续逐卡下指令；这没有满足把包交给开发Agent后持续做完的预期。
- 旧文档把正式CI/候选打包放在V3-21，把很多可运行性风险延迟到后期；应在开始就有最小构建，并随着每个真实切片回归。
- 旧验收定义存在，但可执行脚本主要验证原型、参考合同和交接图，没有替产品自动执行所有验收。不能把原型的通过数字当交付成熟度。
- 有风险前置条款，却没有让未闭合的真实Cursor/手机能力实际阻断“全自动已完成”的结论。
- 未给出顺畅的“自动继续/保存断点/解除阻塞/复核/候选/发布审批”全过程。禁止自动发布是合理边界，但不能替代准备到随时可发布。

实现者也有独立责任：公开配对、自授权限、未鉴权改稿、当前稿/上次稿混用、不按生产前端协议测试、硬编码PASS，与原规格并不一致。不能把全部问题归因于文档长度，也没有依据给各方分配精确责任百分比。

这次修的是执行控制，不推翻设计，不重新抄写全部规格，不要求无依据换模型或重写语言。

## 2. 唯一终点与发布授权

### 完整交付目标

R01–R10按原义全部完成，原96项均有足够层级证据；实际Windows包能从零启动，并完成真实Android+豆包输入法+选定Cursor版本的主要流程，达到独立验收认可的候选状态。

V3是设计代号，不自动等于应用v3.0.0；候选版本号从真实仓库读取后拟定并批准。

| 状态 | 可以做/可以宣称 | 不能混淆 |
|---|---|---|
| DEVELOPMENT | 继续编码、生产测试、构建带明确标识的隔离开发包 | 不能称已完成、日用可替换 |
| INTEGRATION_READY | 已完成若干真实切片，可请人验收这些切片 | 不等于完整V3，不等于Release |
| CANDIDATE_BUILT | 有真实可追溯包，供隔离试用 | 打包成功不是原生验收成功 |
| RELEASE_READY | 全范围、质量、最终包与独立复核达标 | 不等于已有公开发布许可 |
| PUBLISHED | 用户批准具体制品后，实际发布动作成功并验证下载 | 不可用准备好的Release文案冒充已发布 |

开发Agent可以连续完成前四类中的授权工作，真实发布仍需要用户明确批准。没有批准时把包、校验值、说明与发布操作准备齐全，不把“禁止Release”用作不打包、不闭合产品的理由。

## 3. 范围固定，支持边界明确

保留：空闲无浮窗；活动时非激活小HUD；单页手机Composer；语音输入法原路径；截电脑、相册、裁剪、标注、轻量白板；编号说明；图片先文字后；不按Enter；当前稿与上次召回；部分/未知结果恢复；持久化；可选BYOK；新手引导、设置、隔离迁移、回退。

不增加：云账号、远程桌面、自动发消息、无限白板、复杂项目管理。本轮macOS/Linux/公网隧道仍后置，不能悄悄把本轮白板或BYOK后置。

首发支持矩阵按真实环境填写：Windows版本与缩放、Android型号/系统/浏览器/豆包输入法版本、Cursor版本与图像输入能力。不要声称“支持所有Agent”。先让至少一组主目标真实通过，再扩支持范围。

### 不可用降级不得冒充主目标完成

原生可访问性观察、受目标产品支持的接口等方案，必须先调查、验证再采用，不能假定某接口一定可用。UIA不可观察时，明确半自动确认可以作为未支持目标的退路；不能把主目标永久降为逐图手动确认后仍宣称原设计“一键图文”完成。

若主目标在现有约束下确需新增扩展、变更安装步骤或降低自动化，提供实际实验结果、替代方案、用户影响及建议，请求一次具体变更决定；不要无声修改验收。无论选哪条路径都不得盲目sleep后冒称接收完成。

## 4. 持续推进，不是一次写完所有代码

一次只聚焦一个端到端小切片：读对应规格→先建立会失败的真实测试→修实现→接生产入口→回归→记录证据→更新断点→继续下一依赖已满足的切片。

“逐切片实现”不再等于“每切片必须用户再说继续”。在同一有执行预算的会话中持续推进。上下文/工具会话结束时把事实落盘，下一次一句继续即可恢复；文档不能让已经停止的Agent自动在后台运行。

读上下文分两层：首次读整体目标、状态与架构；日常只注入短规则、当前切片、相关接口/反例和当前CHECKPOINT，必要时回查原规格。不要每个小任务要求重新读完1807行，也不要只读摘要忘了强约束。

### 原接口合同要变成真实集成约束

当前draft/asset/bundle/intent/attempt结构各有唯一schema或类型定义，明确唯一写入者、必填字段、状态所有权和迁移版本。双方消费同一规范；需要分别实现时由生产序列化器生成互验数据。

上传后的asset_refs必须由服务端解析为已鉴权、已完成的成品资产；缺失/乱序/重复明确拒绝。客户端不偷偷补后端内部assets对象；测试也不能补。测试图保留可识别编号/色块/保密区，用解码后的成品像素和目标图验证，而非只数附件ID。

## 6. 必须贯穿开发的9条真实故事

这些不是新增产品需求，是把原验收串成真实使用路线；最终仍映射回96条，不用9个故事取代全部验收。

| 故事 | 用户操作 | 观察点 |
|---|---|---|
| J1 无图语音 | 连接→手机输入法说两段→Alt+I→继续第三段 | 保留输入法回改/空白；原文不等AI；HUD按需出现与隐藏；不发Enter |
| J2 截图修改 | 截电脑→裁剪→遮挡测试保密区→画箭头→补说明→插入 | 正确鉴权加载；只投成品；坐标/尺寸/像素正确；主目标真实有附件 |
| J3 相册多图 | 选两张→分别标注→改顺序→插入 | 两张均完成/保存；顺序与文字对应；无遗漏/重复；非localhost实际手机路径 |
| J4 白板表达 | 新白板→三笔+图形+编号→撤销/重做→完成→重新编辑→插入 | 第一笔可撤销；场景可继续编辑；双指手势不产生意外笔画；导出不取决于屏幕缩放 |
| J5 错焦点恢复 | A未投成功→开始B→改选Composer→召回A | B保留；A精确重试；同类不同窗口/文档不能当同目标；未知结果真实选择 |
| J6 故障恢复 | 图片中断/断网→重连；投图1后切目标；崩溃→重启 | 只恢复数据不重放动作；持久化ACK真实；已执行步骤不退回“零步骤” |
| J7 完整设置 | 从零引导→改热键→可选配BYOK→错误/超时→继续输入 | 正式UI可达；无Key主路径完整；密钥不进日志；旧结果不覆盖新稿 |
| J8 成品试用 | 干净Windows解压→配真手机→完成J1–J7→退出/回退 | 无开发机依赖；最终包与证据同SHA/哈希；不写坏旧版数据 |
| J9 授权失败 | 未配对/拒绝/撤销/过期设备请求读图/改稿/截图/插入 | 权限由电脑批准；拒绝零副作用；诊断不含图像/正文/密钥 |

单元测试允许替身；生产前端集成不能替换自己的桥接后端或偷偷补协议；真实Cursor验收不能替换目标应用。第三方付费API的错误路径可mock，但声明真实BYOK兼容仍需批准后做有限真实探测，不自动扩大消费。

## 7. 阻塞管理：环境缺失不是万能标签

每个阻塞写五件事：缺什么、实际探测了什么、影响哪些验收、谁能解除、最小动作是什么；再列不受影响可继续的工作。

- 代码根本没实现/反例已经失败：FAIL，继续修。
- 有实现但还没实际运行：NOT_RUN，不等于BLOCKED_NATIVE。
- 真实设备/系统授权/应用版本不可访问：BLOCKED_ENV（沿用表可写BLOCKED_NATIVE），仅约束相关用例。
- 需要设计变更：DECISION_REQUIRED，给具体方案与代价，不让用户重述已有需求。
- 工具额度或上下文结束：CHECKPOINTED，下次从已记录步骤继续，不改变产品完成状态。

无ADB不等于手机验收绝对不可执行：可以采用用户授权的手动录屏+步骤执行与脱敏事件记录；ADB只是自动化途径之一。真实豆包必须运行在真实手机，人工操作同样有效，不能用mock代替。

本轮已知是某个实现环境缺目标设备；没有拿到完整Grok执行对话，不能断言用户本人的设备无法使用，或用户没授权。

## 8. 完成判定不能由实现者一句话决定

每项范围分别记录：实现状态、生产接通状态、自动测试、原生测试、独立复核。示例：代码DONE / 接通FAIL / 自动部分通过 / 真机BLOCKED；不能压成一个绿色DONE。

保留原96项定义。原型检查、接口样例检查、文档图无环检查属于工具自测，不计产品通过率。14项审计反例是定向检查，不能据12个失败反推整体只有某个完成百分比。

PASS最低证据：固定源码、真实命令/退出码、环境、实际输入/观察与期望、证据文件；原生项还绑定候选包哈希和目标版本。testcase必须实际执行且非skip；运行层级必须满足该验收，不以源码路径替代。

独立评审检查断言是否证明期望、是否走生产入口、是否真的观察目标；不能只读开发者摘要。对真实UI做固定尺寸/主题/DPI比对，并使用，而不只是比截图漂亮不漂亮。

本包检查器能筛查丢项、静态文件冒充运行证据、旧SHA、变更哈希、无执行/跳过的JUnit等，但不能鉴定一份制作精良的假日志。规则与检查器如果能被同一开发者随意改掉，都不能当安全隔离；CI/审查保护要在实际仓库中建立。没有独立来源和评审，不能保证“彻底杜绝假PASS”。

## 9. CI与候选：从第一天可执行

S0需把以下工作真正接到隔离分支的CI，不是仅在文档列命令：锁定Python/Node运行环境与实际依赖（含Pillow等）；后端单元/协议反例；前端类型检查、生产构建、生产页面到真实本地桥接的浏览器测试；Windows最小打包及资源检查。命令由实际项目工具定义，不存在就实现，不用echo代替。

带桌面操作的测试与普通云端CI区分：有人登录的授权Windows测试会话+真实Cursor才验证焦点/粘贴；真实Android才验证输入法/多指/键盘行为。CI绿不能代替这些证据。

开发用测试权限与发布权限隔离。发布工作流应消费经过审查的固定制品或可追溯重建并重验的制品，不能标签一推就无门槛发布。仓库支持时采用受保护发布environment人工批准；所用GitHub账号只有一个时，不要盲开“禁止自审”导致唯一有权用户无法批准，选择适合真实账号结构的控制。

## 10. RELEASE_READY的具体含义

必需功能都可操作且按原96项验证；安全、错目标、漏图、重复投递、数据丢失等P0为零；本轮必需功能缺失的P1不能靠写known issue过关。可接受的小视觉瑕疵应由用户明确认可且不改变核心动作，不能无限追求无关抛光。

目标支持矩阵至少一组主目标通过，未支持组合清楚提示。原时间/压力/性能预算保留，不另外加未经用户认可的新平台与大工程。

测试从最终生产包启动，包含干净Windows、真实Android、真实Cursor以及白板和召回，不只是源代码运行。包附网页资源、图标、依赖/许可证、版本、说明；验证无开发路径、个人Key、私密截图。代码签名的真实状态明确说明；没有签名不能宣称已签，也不擅自购买证书。

最终证据以CI artifact/独立证据目录保存，避免为了提交证据而无限改变被测源码SHA。若合并/squash/版本变更得到新发布提交，需要重新构建、核对差异与重跑受影响验收，不能用旧SHA报告证明新包。所有发布资源以实际下载后哈希核对。

## 11. 发布审批单（准备好，不自动执行）

提交：源分支和完整SHA、应用版本、构建工作流run ID、制品路径与SHA256、支持矩阵、原96项结果、独立功能与视觉评审、已知限制、迁移/回退、准备发布的说明、是否签名。

用户批准的是这份具体制品及相应发布动作，而不是让Agent对任意后续SHA永久自动发版。审批前只交可试用候选；批准后才按已批准范围创建标签/Release/所需合并。发布下载失败或哈希不同必须停止，不能静默换包。

## 12. ako不应承担的工作

不应逐卡安排、检查每个字段、猜测依赖、自己找每个PASS是不是假的。开发Agent承担编码与第一轮回归；独立复核承担证据与产品检查。

不可代替的少量人类动作：设备/系统授权、确认操作手感、必要的真实手机动作、最终具体发布批准。应集中成一份清楚的测试脚本，一次会话完成多个流程；不要零散追问已给出的需求。若主环境确实不可用，要早给明确缺口，不能在写满24个模块后才说缺手机。
